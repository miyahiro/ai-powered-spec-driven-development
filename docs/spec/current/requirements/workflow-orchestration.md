# ワークフロー・エージェント連携の要求

## 目的・対象範囲

対話の窓口を一本化し、役割とスキルを使い分けて、承認済みの内容から次の工程へ進める。状況確認、中断・再開、ユーザーによるスキル直接指定も対象とする。

状態: 要求定義ドラフト。

出典: [docs/idea/intial-idea.md](../../../idea/intial-idea.md) 第3・6・7・9・12章。共通要求: [common.md](common.md)。

## 機能要件・業務ルール

| ID | 要求 |
| --- | --- |
| REQ-WF-001 | 受付時に変更種別、目的、範囲、既存案件の有無、承認者と役割を確認し、安定した変更 ID を付けること。Git 未初期化・初回コミット前でも受付・壁打ちは開始できること。正式な変更管理の開始前に人の許可を得て必要な Git 初期化・初回コミット・ブランチ準備を行い、変更 ID とブランチ・基点コミットを対応付けること。以降は1変更単位の全工程を同じブランチで扱うこと。大きな案件の分割は人に提案して判断を求めること。 |
| REQ-WF-002 | オーケストレーターが人との窓口となり、必要な担当とスキルを選ぶこと。サブエージェントの質問・承認要求を集約し、ユーザーへ次に必要な操作を示すこと。全役割を毎回起動する必要はない。 |
| REQ-WF-003 | 各役割に目的、入力、出力、編集範囲、利用可能なツール、停止条件を定義できること。委任時には変更 ID、ブランチ・版、要件・タスク ID、入力参照、禁止事項を渡し、返却で成果物、変更概要、証拠、未解決事項、次の作業を受け取ること。 |
| REQ-WF-004 | アイデア、要件、外部設計、内部設計、タスク分解・整合性確認、開発・テストの順を扱うこと。前提不足の後続作業を止め、前工程への差し戻しを同じ変更単位で記録できること。成果物が不要な工程は、理由・参照版・対象外または変更なしの承認を記録して次へ進めること。 |
| REQ-WF-005 | アイデア・要件・外部設計を発注者、内部設計・開発完了を技術責任者が承認すること。同一人物の兼任と、VS Code を使わない承認者の回答の代理記録を扱い、代理記録者と承認者を区別すること。 |
| REQ-WF-006 | 承認は工程単位とし、その工程の対象成果物一式と版、役割、承認者、日時、判断、回答の出所を記録すること。承認記録や進行状態の更新は承認対象の版に含めず、記録したことだけで承認を無効にしないこと。コメントや曖昧な発言は承認と扱わず、成果物の変更に影響する工程と後続について再承認を求めること。 |
| REQ-WF-007 | フェーズと進行状態を分離し、ドラフト、作業中、阻害、承認待ち、承認済み、完了、中断を区別すること。開発完了、Git 操作の許可、マージ済み、本番反映を混同しないこと。具体的な状態名は設計で決定する。 |
| REQ-WF-008 | 状況確認は読み取り専用とし、現在フェーズ、質問・承認待ち、参照先、許可範囲、次の人の操作を返すこと。中断時は新規作業を止め、実行中操作を安全に区切って再開位置を記録すること。 |
| REQ-WF-009 | 別の会話でも保存成果物から再開できること。現在ブランチ、手動編集、原本の版、承認、質問、残タスク、未実施検証、許可範囲を確認し、不一致・不足を解消するまで関連作業を再開しないこと。 |
| REQ-WF-010 | ユーザーがスキルを直接指定した場合も、その工程・操作に必要な前提を確認すること。承認を必要としない壁打ち・質問整理・状況確認・読み取り専用レビューは未承認でも利用できること。レビュー担当は結果を返すだけとし、レビュー依頼だけではファイル・状態を書き換えず、実装へ進まないこと。レビュー結果の保存は、人の依頼または合意した保存範囲に基づきオーケストレーターが行い、保存だけで承認・タスク完了・工程移行を行わないこと。作業による変更は対応する状態と引き継ぎへ反映すること。 |
| REQ-WF-011 | サブエージェントを使えない場合は同じ手順を役割切り替えで実行できること。ただし役割名を変えただけでは独立レビューとせず、別のレビュー担当エージェント、または実装担当とは異なる人による確認を用いること。対象版・確認者・指摘・確認結果を記録し、別エージェントが未実施ならそう表示すること。代替の人による確認が完了すれば、別エージェントの利用を必須にしないこと。 |

### 必要な役割

個々の設定ファイル数・役割の統合方法は設計で決めるが、以下の責務を欠落させない。

| 役割 | 求める責務 |
| --- | --- |
| オーケストレーター | 状態・担当・質問・承認要求・引き継ぎの管理 |
| アイデア支援 | 課題、価値、候補、対象範囲の整理 |
| 要件分析 | シナリオ、業務ルール、機能・非機能要件、受入条件の整理 |
| 外部設計 | 発注者向けの UI・帳票・外部連携の仕様化 |
| 内部設計 | DDD、依存、データ・処理、共通機能、運用・テストの設計支援 |
| タスク計画 | 設計からの作業分解、依存順、TDD の検証順序 |
| TDD 実装 | テスト先行実装、リファクタリング、検証証跡 |
| 独立レビュー・検証 | 仕様間・実装間の整合性と検証結果の確認 |

### この機能で必要なスキル相当の手順

名称は識別用の候補であり、Copilot の実装済みコマンド名ではない。

| 手順候補 | 期待する入出力・結果 |
| --- | --- |
| `change-intake` | 依頼・現在ブランチ・既存成果物から、変更単位と受付情報を整理 |
| `workflow-status` | 変更 ID と保存状態から、読み取り専用で現在地と次の操作を提示 |
| `workflow-resume` | 保存状態と現在の成果物を照合し、再開位置と不足条件を提示 |
| `clarification` | 疑問から質問を作成し、人の回答を決定・正式成果物へ反映 |
| `phase-handoff` | 成果物・質問・承認から移行条件を確認し、承認要求と引き継ぎを作成 |

各スキルに適用条件、必須入力、出力形式、利用ツール、成功条件、停止・再開条件が必要である。この条件は他文書のスキルにも適用する。

## 非機能要件

| ID | 要求 |
| --- | --- |
| NFR-WF-001 | 状況と阻害理由を、全会話を読み返さなくても保存記録から確認できること。承認対象の参照先と必要な承認役割がわかること。 |
| NFR-WF-002 | 同じ共有ファイルへの書き込みを直列化すること。並行委任を用いる場合は読み取りや編集先が独立した作業に限定し、未承認事項を前提に後続工程を並行実行しないこと。役割の並行実行の検証は共通要求の対象外とする。 |

## 受入条件

| ID | 対象 | 条件・期待結果 |
| --- | --- | --- |
| AC-WF-001 | REQ-WF-001、REQ-WF-002 | 新規・追加・修正の受付で種別・既存案件・担当役割を確認する。Git 未初期化でも壁打ちを開始できる。正式な変更管理までに Git 準備と基点を確認し、許可がなければ初期化・コミット・ブランチ作成を行わない。工程ごとの別ブランチを作らない。 |
| AC-WF-002 | REQ-WF-002、REQ-WF-003 | 設計を委任すると担当に入力・版・編集範囲が渡り、質問がユーザー窓口へ集約される。返却から成果物・証拠・未解決事項を確認できる。 |
| AC-WF-003 | REQ-WF-004、REQ-WF-005、REQ-WF-006 | 外部設計または理由付きの対象外判断が未承認のまま内部設計・実装を依頼すると止まる。対象外の承認があれば不要な設計書を生成せず進める。複数文書の要求定義を工程単位で承認でき、承認記録や進行状態だけの更新では承認を失わない。対象成果物を変更すると、影響する工程の旧承認を流用しない。 |
| AC-WF-004 | REQ-WF-005、REQ-WF-006 | 発注者のコメントを持ち帰っても承認待ちを維持する。対象版への明示的な承認と出所が確認できた場合だけ、発注者と代理記録者を区別して記録する。 |
| AC-WF-005 | REQ-WF-007、REQ-WF-008、NFR-WF-001 | 状況確認の前後で保存ファイルが変わらず、承認待ちと次の操作が表示される。開発完了時にもマージ未実施を確認できる。 |
| AC-WF-006 | REQ-WF-008、REQ-WF-009 | 質問待ちで中断し、別会話で再開すると、未解決質問を維持する。手動回答は意味・出所を確認して正式成果物へ反映し、回答だけでは承認済みにしない。 |
| AC-WF-007 | REQ-WF-009、REQ-WF-010 | 登録済みと別のブランチからの再開や、必要な承認のない後続作業は止まる。未承認のドラフトでも壁打ち・質問整理・状況確認・読み取り専用レビューを直接利用できる。レビューだけの依頼でファイル・状態を変更しない。 |
| AC-WF-008 | REQ-WF-011 | サブエージェントが使えない環境で役割切り替えだけを行うと、独立確認未実施と表示する。その後、実装担当とは異なる人が対象版を確認し、確認者・指摘・結果を記録すれば独立レビューを完了できる。人の完了承認は別途必要とする。 |
| AC-WF-009 | NFR-WF-002 | 共有ファイルを更新する手順に書き込みの直列化と版の確認が定義されている。並行実行の動作試験は対象外であり、その未実施を理由に完了を止めない。 |
| AC-WF-010 | REQ-WF-010 | レビューだけの依頼ではファイルが変わらない。「結果を記録して」と依頼すると、オーケストレーターが合意した保存先へ結果だけを保存し、原本・タスク完了・承認状態を変更しない。 |
