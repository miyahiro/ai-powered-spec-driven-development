# ワークフロー・エージェント連携の要求

## 目的・対象範囲

対話の窓口を一本化し、役割とスキルを使い分けて、承認済みの内容から次の工程へ進める。状況確認、中断・再開、ユーザーによるスキル直接指定も対象とする。

状態: 要求定義ドラフト。

出典: [docs/idea/intial-idea.md](../../../idea/intial-idea.md) 第3・6・7・9・12章。共通要求: [common.md](common.md)。

### 必要な役割

個々の設定ファイル数・役割の統合方法は設計で決めるが、以下の責務を欠落させない。

| 役割 | 求める責務 | 担当する機能 |
| --- | --- | --- |
| オーケストレーター | 状態・担当・質問・承認要求・引き継ぎの管理、共有記録の更新、原本更新の統合 | FUN-COM-001、FUN-WF-001〜007、FUN-SPEC-006、FUN-SPEC-007、FUN-SPEC-009 |
| アイデア支援 | 課題、価値、候補、対象範囲の整理 | FUN-SPEC-001 |
| 要件分析 | シナリオ、業務ルール、機能・非機能要件、受入条件の整理 | FUN-SPEC-002 |
| 外部設計 | 発注者向けの UI・帳票・外部連携の仕様化 | FUN-SPEC-003 |
| 内部設計 | DDD、依存、データ・処理、共通機能、運用・テスト、設計判断記録の設計支援 | FUN-SPEC-004、FUN-SPEC-005 |
| タスク計画 | 設計からの作業分解、依存順、TDD の検証順序 | FUN-DEV-001 |
| TDD 実装 | テスト先行実装、リファクタリング、検証証跡 | FUN-DEV-002、FUN-DEV-004 |
| 独立レビュー・検証 | 仕様間・実装間の整合性と検証結果の確認 | FUN-DEV-003、FUN-SPEC-008 |

### 提供する機能

agent・skill の名称と分割は設計で決める。ただし以下の機能を欠落させない。各機能には適用条件（入力・前提）、結果、停止条件を持たせる。この規則は他文書の機能にも適用する。

| ID | 機能 | 入力・前提 | 結果 | 停止・対象外 | 対応 REQ | 大分類 |
| --- | --- | --- | --- | --- | --- | --- |
| FUN-WF-001 | 変更受付 | 依頼、現在ブランチ、既存成果物。Git 未初期化でも可 | 変更 ID・種別・目的・範囲・承認役割・Git 準備状況の整理 | 対象案件が複数候補、範囲不明なら人に確認する。承認者を推測登録しない | REQ-WF-001 | CAT-FLOW 工程進行 |
| FUN-WF-002 | 窓口と担当への委任 | 受付済みの案件、必要な工程・担当 | 担当選択、委任、返却の検査、質問・承認要求の集約、役割切り替え時の独立性表示 | 全役割の毎回起動、並行実行は求めない。実際の成果と一致しない成功報告を採用しない | REQ-WF-002、REQ-WF-003、REQ-WF-011 | CAT-FLOW 工程進行 |
| FUN-WF-003 | 工程進行と承認管理 | 工程成果物一式・質問・版・承認・許可 | 承認依頼と前提確認、人の回答の記録、次工程への引き継ぎ、差し戻し、状態の区別 | 必須質問・成果物不足・旧版承認では移行しない。AI の自己承認、本人認証は対象外 | REQ-COM-003、REQ-WF-004、REQ-WF-005、REQ-WF-006、REQ-WF-007 | CAT-FLOW 工程進行 |
| FUN-WF-004 | 状況確認 | 変更 ID または案件候補 | 現在工程、阻害、質問・承認待ち、参照先、許可範囲、次の人の操作を読み取り専用で提示 | 保存・状態更新はしない。案件を一意に選べなければ候補を示す | REQ-WF-008 | CAT-FLOW 工程進行 |
| FUN-WF-005 | 中断と再開 | 変更 ID、保存状態、現在の成果物 | 新規作業の停止、再開位置の記録、再開時の照合結果と不足条件 | ブランチ・版・許可・必須質問の不一致が解消するまで関連作業を再開しない | REQ-WF-008、REQ-WF-009 | CAT-FLOW 工程進行 |
| FUN-WF-006 | 質問整理と回答反映 | 未解決事項・新たな疑問、関連工程 | 選択肢・推奨・影響・確認期限を付けた質問、人の回答と出所の記録、決定・正式成果物への反映 | 回答が曖昧、影響する承認の扱い不明なら確定しない。未確定を推測で決めない | REQ-COM-002 | CAT-FLOW 工程進行 |
| FUN-WF-007 | スキルの直接指定と読み取り専用レビュー | ユーザーが指定した手順、その工程の前提 | 必要な前提の確認、承認不要の壁打ち・質問整理・状況確認・レビューの提供、結果保存の別操作化 | レビュー依頼だけでは書き換え・実装・承認・工程移行をしない | REQ-WF-010 | CAT-FLOW 工程進行 |

## 非機能要件

| ID | 要求 |
| --- | --- |
| NFR-WF-001 | 状況と阻害理由を、全会話を読み返さなくても保存記録から確認できること。承認対象の参照先と必要な承認役割がわかること。 |
| NFR-WF-002 | 同じ共有ファイルへの書き込みを直列化すること。並行委任を用いる場合は読み取りや編集先が独立した作業に限定し、未承認事項を前提に後続工程を並行実行しないこと。役割の並行実行の検証は共通要求の対象外とする。 |

## 受入条件

| ID | 対象 | 条件・期待結果 |
| --- | --- | --- |
| AC-WF-001 | REQ-WF-001、REQ-WF-002 | 新規・追加・修正の受付で種別・既存案件・担当役割を確認する。Git 未初期化でも壁打ちを開始できる。正式な変更管理までに Git 準備と基点を確認し、許可がなければ初期化・コミット・ブランチ作成を行わない。工程ごとの別ブランチを作らない。 |
| AC-WF-002 | REQ-WF-002、REQ-WF-003 | 設計を委任すると担当に入力・版・編集範囲が渡り、質問がユーザー窓口へ集約される。返却から成果物・証拠・未解決事項を確認できる。 |
| AC-WF-003 | REQ-WF-004、REQ-WF-005、REQ-WF-006 | 外部設計または理由付きの対象外判断が未承認のまま内部設計・実装を依頼すると止まる。対象外の承認があれば不要な設計書を生成せず進める。複数文書の要求定義を工程単位で承認でき、承認記録や進行状態だけの更新では承認を失わない。対象成果物を変更すると、影響する工程の旧承認を流用しない。 |
| AC-WF-004 | REQ-WF-005、REQ-WF-006 | 発注者のコメントを持ち帰っても承認待ちを維持する。対象版への明示的な承認と出所が確認できた場合だけ、発注者と代理記録者を区別して記録する。 |
| AC-WF-005 | REQ-WF-007、REQ-WF-008、NFR-WF-001 | 状況確認の前後で保存ファイルが変わらず、承認待ちと次の操作が表示される。開発完了時にもマージ未実施を確認できる。 |
| AC-WF-006 | REQ-WF-008、REQ-WF-009 | 質問待ちで中断し、別会話で再開すると、未解決質問を維持する。手動回答は意味・出所を確認して正式成果物へ反映し、回答だけでは承認済みにしない。 |
| AC-WF-007 | REQ-WF-009、REQ-WF-010 | 登録済みと別のブランチからの再開や、必要な承認のない後続作業は止まる。未承認のドラフトでも壁打ち・質問整理・状況確認・読み取り専用レビューを直接利用できる。レビューだけの依頼でファイル・状態を変更しない。 |
| AC-WF-008 | REQ-WF-011 | サブエージェントが使えない環境で役割切り替えだけを行うと、独立確認未実施と表示する。その後、実装担当とは異なる人が対象版を確認し、確認者・指摘・結果を記録すれば独立レビューを完了できる。人の完了承認は別途必要とする。 |
| AC-WF-009 | NFR-WF-002 | 共有ファイルを更新する手順に書き込みの直列化と版の確認が定義されている。並行実行の動作試験は対象外であり、その未実施を理由に完了を止めない。 |
| AC-WF-010 | REQ-WF-010 | レビューだけの依頼ではファイルが変わらない。「結果を記録して」と依頼すると、オーケストレーターが合意した保存先へ結果だけを保存し、原本・タスク完了・承認状態を変更しない。 |
