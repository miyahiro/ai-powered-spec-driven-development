# ワークフロー・エージェント連携の要求

## 目的・対象範囲

対話の窓口を一本化し、役割とスキルを使い分けて、承認済みの内容から次の工程へ進める。状態の遷移は Human-in-the-loop とし、人は対話で判断（回答・承認・許可・中断等）を答え、AI がその回答を確認して管理下の経路で記録・遷移させる。状況確認、中断・再開、ユーザーによるスキル直接指定も対象とする。

状態: 要求定義ドラフト。

出典: [docs/idea/intial-idea.md](../../../idea/intial-idea.md) 第3・6・7・9・12章。共通要求: [common.md](common.md)。

| REQ-WF-007 | CAT-FLOW 工程進行 | FUN-WF-003 | フェーズと進行状態を分離し、ドラフト、作業中、阻害、承認待ち、承認済み、完了、中断を区別すること。開発完了、Git 操作の許可、マージ済み、本番反映を混同しないこと。具体的な状態名は設計で決定する。 |

| REQ-WF-010 | CAT-FLOW 工程進行 | FUN-WF-007 | ユーザーがスキルを直接指定した場合も、その工程・操作に必要な前提を確認すること。承認を必要としない壁打ち・質問整理・状況確認・読み取り専用レビューは未承認でも利用できること。レビュー担当は結果を返すだけとし、レビュー依頼だけではファイル・状態を書き換えず、実装へ進まないこと。レビュー結果の保存は、人の依頼または合意した保存範囲に基づきオーケストレーターが行い、保存だけで承認・タスク完了・工程移行を行わないこと。作業による変更は対応する状態と引き継ぎへ反映すること。 |
| REQ-WF-011 | CAT-FLOW 工程進行 | FUN-WF-002 | サブエージェントを使えない場合は同じ手順を役割切り替えで実行できること。ただし役割名を変えただけでは独立レビューとせず、別のレビュー担当エージェント、または実装担当とは異なる人による確認を用いること。対象版・確認者・指摘・確認結果を記録し、別エージェントが未実施ならそう表示すること。代替の人による確認が完了すれば、別エージェントの利用を必須にしないこと。 |
| REQ-WF-012 | CAT-FLOW 工程進行 | FUN-WF-008 | 状態の遷移は対話で進めること。質問・回答・決定・工程承認・操作許可・工程移行・中断・再開・差し戻しについて、AI は必要な人の判断を対話で求め、回答を確認したら、人にコマンドや request の作成・実行を求めずに管理下の経路（REQ-TOOL-009）で記録・遷移すること。Git 操作・マージ・本番反映は自動記録・自動実行の対象外とし、REQ-TOOL-002 の個別許可と人の操作に従うこと。 |
| REQ-WF-013 | CAT-FLOW 工程進行 | FUN-WF-008 | 阻害となる質問の登録・解消、工程承認の記録など、移行の前提が満たされた時点で、AI は人に別の指示を求めずに進行状態と工程を遷移させること。前提を検証できない、または満たさない場合は遷移せず、阻害理由と必要な人の判断・操作を示すこと。中断・再開・差し戻しは人の依頼を対話で確認した場合だけ記録すること。AI 自身の判断だけで承認・許可・中断・差し戻しを記録しないこと。 |
| REQ-WF-014 | CAT-FLOW 工程進行 | FUN-WF-008 | 工程承認と操作許可は、AI が対象（工程と成果物一式の版・対象一覧・承認役割、または操作・対象・範囲）を対話で示した後に、登録された役割の人から定型の肯定回答を得た場合だけ記録すること。曖昧・条件付き・保留・疑問の回答、「続けて」、対象を示す前の回答、別の対象への回答は記録せず聞き直すこと。提示から回答までに対象の版が変われば旧版への回答として扱わず再提示すること。1つの回答を提示外の工程・操作・範囲へ広げないこと。質問への回答は要旨を示して確認し、意味を確定できなければ聞き直すこと。 |
| REQ-WF-015 | CAT-FLOW 工程進行 | FUN-WF-008、FUN-WF-004 | 自動で記録・遷移するたびに、記録した内容、人の回答の要旨、回答者、時刻、出所、新しい状態と版を対話で報告すること。人が後から自動記録の一覧を状況確認で確かめられること。誤った記録は既存の記録を書き換えず、人の確認を得た新しい記録や差し戻しで正すこと。 |
| REQ-WF-016 | CAT-FLOW 工程進行 | FUN-WF-008 | 記録の方式は自動記録を既定とすること。手動利用は、人が対話で手動を選んだ場合（その会話の間）、または人が設定で手動を既定にした場合に限ること。自動記録の前提（REQ-TOOL-009）が確認されていない間は、自動でも手動でも記録せずに止め、確認手順と、手動利用を選べることを示すこと。手動利用では AI が操作案と内容の説明を示し、人が確認して実行すること。案の提示や人の実行前の状態を記録済み・遷移済みと表示しないこと。どちらの方式でも人の判断の求め方と記録の条件（REQ-WF-014）は変えないこと。 |
| REQ-WF-017 | CAT-FLOW 工程進行 | FUN-WF-002 | 窓口は、担当の返却を、文書を読み直さずに、返却された版と実ファイルの版の比較、編集範囲・担当・工程の確認で照合すること。版が一致しない場合は返却を採用せず、その場合だけ差分を確かめること。版の一致を内容の正しさの確認と扱わず、内容の確認はレビュー担当と人が行うこと。 |
| REQ-WF-018 | CAT-FLOW 工程進行 | FUN-WF-004、FUN-WF-005 | ランナーは、状況確認に必要な項目（工程・状態、期限の来た質問、承認待ちと承認する人、承認後に成果物が変わった工程、途中の更新、タスクの件数と未検証、許可の範囲、取り込みの状況、次に必要なこと、依頼時の記録の一覧）を、読み取り専用の操作で集計して返すこと。あわせて、状態を変える操作のたびに同じ形の要約を案件の Scratchpad に書き出すこと。自動記録の環境では集計の操作を使い、ランナーを実行できない間（確認待ち・手動利用）は要約ファイルを読むこと。要約ファイルを使う場合は、最後の記録の時点の内容であり、その後の手での編集による変化は確かめていないことを示すこと。要約ファイルはランナーだけが書き、工程の承認の対象に含めないこと。 |

### 提供する機能

agent・skill の名称と分割は設計で決める。ただし以下の機能を欠落させない。各機能には適用条件（入力・前提）、結果、停止条件を持たせる。この規則は他文書の機能にも適用する。

| ID | 機能 | 入力・前提 | 結果 | 停止・対象外 | 対応 REQ | 大分類 |
| --- | --- | --- | --- | --- | --- | --- |
| FUN-WF-001 | 変更受付 | 依頼、現在ブランチ、既存成果物。Git 未初期化でも可 | 変更 ID・種別・目的・範囲・承認役割・Git 準備状況の整理 | 対象案件が複数候補、範囲不明なら人に確認する。承認者を推測登録しない | REQ-WF-001 | CAT-FLOW 工程進行 |
| FUN-WF-002 | 窓口と担当への委任 | 受付済みの案件、必要な工程・担当 | 担当選択、パスと版による委任、版の比較による返却の照合、質問・承認要求の集約、役割切り替え時の独立性表示 | 全役割の毎回起動、並行実行は求めない。実際の成果と一致しない成功報告を採用しない | REQ-WF-002、REQ-WF-003、REQ-WF-011、REQ-WF-017 | CAT-FLOW 工程進行 |
| FUN-WF-003 | 工程進行と承認管理 | 工程成果物一式・質問・版・承認・許可 | 承認依頼と前提確認、人の回答の記録、次工程への引き継ぎ、差し戻し、状態の区別。記録と遷移の進め方は FUN-WF-008 | 必須質問・成果物不足・旧版承認では移行しない。AI の自己承認、本人認証は対象外 | REQ-COM-003、REQ-WF-004、REQ-WF-005、REQ-WF-006、REQ-WF-007 | CAT-FLOW 工程進行 |
| FUN-WF-004 | 状況確認 | 変更 ID または案件候補 | 現在工程、阻害、質問・承認待ち、承認後に変わった工程、参照先、許可範囲、記録の方式、自動記録の一覧、次に必要な人の判断・操作を、ランナーの集計（確認待ちの間は要約ファイル）から読み取り専用で提示 | 保存・状態更新はしない。案件を一意に選べなければ候補を示す。要約ファイルを使った場合はその時点を明示する | REQ-WF-008、REQ-WF-015、REQ-WF-018 | CAT-FLOW 工程進行 |
| FUN-WF-005 | 中断と再開 | 変更 ID、保存状態、現在の成果物 | 新規作業の停止、再開位置の記録、再開時の照合結果と不足条件 | ブランチ・版・許可・必須質問の不一致が解消するまで関連作業を再開しない | REQ-WF-008、REQ-WF-009 | CAT-FLOW 工程進行 |
| FUN-WF-006 | 質問整理と回答反映 | 未解決事項・新たな疑問、関連工程 | 選択肢・推奨・影響・確認期限を付けた質問、人の回答と出所の記録、決定・正式成果物への反映 | 回答が曖昧、影響する承認の扱い不明なら確定しない。未確定を推測で決めない | REQ-COM-002 | CAT-FLOW 工程進行 |
| FUN-WF-007 | スキルの直接指定と読み取り専用レビュー | ユーザーが指定した手順、その工程の前提 | 必要な前提の確認、承認不要の壁打ち・質問整理・状況確認・レビューの提供、結果保存の別操作化 | レビュー依頼だけでは書き換え・実装・承認・工程移行をしない | REQ-WF-010 | CAT-FLOW 工程進行 |
| FUN-WF-008 | 対話による状態の記録と遷移 | 人の対話での回答・依頼、現在の状態と版、記録の方式（既定・人の選択・前提の確認状況） | 判断を求める対象の提示、定型回答の確認、管理下の経路による記録と前提を満たした遷移、記録結果の報告。人が手動を選んだ場合は操作案 | 曖昧な回答・旧版・前提不足では記録・遷移しない。自動記録の前提が未確認なら、手動を選ばれない限り記録を止めて確認手順を示す。AI 単独の判断での承認・許可・中断・差し戻しはしない。Git 操作・マージ・本番反映は対象外 | REQ-WF-012、REQ-WF-013、REQ-WF-014、REQ-WF-015、REQ-WF-016 | CAT-FLOW 工程進行 |

## 非機能要件

| ID | 要求 |
| --- | --- |
| NFR-WF-001 | 状況と阻害理由を、全会話を読み返さなくても保存記録から確認できること。承認対象の参照先と必要な承認役割がわかること。 |
| NFR-WF-002 | 同じ共有ファイルへの書き込みを直列化すること。並行委任を用いる場合は読み取りや編集先が独立した作業に限定し、未承認事項を前提に後続工程を並行実行しないこと。役割の並行実行の検証は共通要求の対象外とする。 |
| NFR-WF-003 | 通常の工程進行で、人が JSON・コマンド・ファイルの版の値を入力・実行しなくてよいこと。人の手間は判断の回答と、AI が示した対象の確認に限ること。 |

## 受入条件

| ID | 対象 | 条件・期待結果 |
| --- | --- | --- |
| AC-WF-001 | REQ-WF-001、REQ-WF-002 | 新規・追加・修正の受付で種別・既存案件・担当役割を確認する。Git 未初期化でも壁打ちを開始できる。正式な変更管理までに Git 準備と基点を確認し、許可がなければ初期化・コミット・ブランチ作成を行わない。工程ごとの別ブランチを作らない。 |
| AC-WF-002 | REQ-WF-002、REQ-WF-003 | 設計を委任すると担当に入力・版・編集範囲が渡り、質問がユーザー窓口へ集約される。返却から成果物・証拠・未解決事項を確認できる。 |
| AC-WF-003 | REQ-WF-004、REQ-WF-005、REQ-WF-006 | 外部設計または理由付きの対象外判断が未承認のまま内部設計・実装を依頼すると止まる。対象外の承認があれば不要な設計書を生成せず進める。複数文書の要求定義を工程単位で承認でき、承認記録や進行状態だけの更新では承認を失わない。対象成果物を変更すると、影響する工程の旧承認を流用しない。 |
| AC-WF-004 | REQ-WF-005、REQ-WF-006 | 発注者のコメントを持ち帰っても承認待ちを維持する。対象版への明示的な承認と出所が確認できた場合だけ、発注者と代理記録者を区別して記録する。 |
| AC-WF-005 | REQ-WF-007、REQ-WF-008、NFR-WF-001 | 状況確認の前後で保存ファイルが変わらず、承認待ち、記録の方式、次に必要な人の判断が表示される。開発完了時にもマージ未実施を確認できる。 |
