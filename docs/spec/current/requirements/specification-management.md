# 仕様・設計・Scratchpad 管理の要求

## 目的・対象範囲

議論、変更単位の記録、システム全体の原本を分離し、合意した内容を次工程へ引き継ぐ。要件・外部設計・内部設計の作成支援と、追加・修正時の影響分析を含む。

状態: 要求定義ドラフト。

出典: [docs/idea/intial-idea.md](../../../idea/intial-idea.md) 第4・5・7・10・12章。共通要求: [common.md](common.md)。

## 機能要件・業務ルール

| ID | 要求 |
| --- | --- |
| REQ-SPEC-001 | 壁打ちで課題、利用者、価値、候補・代替案、範囲、対象外を整理できること。議論中の候補と採用した内容を区別すること。 |
| REQ-SPEC-002 | 利用者・目的、シナリオ、機能要件、業務ルール、データの意味、権限、制約、依存先、非機能要件、受入条件を整理できること。要件 ID・受入条件 ID を付与すること。 |
| REQ-SPEC-003 | 要件原本を大きな機能ごとに分け、同じ文書に機能・非機能要件・受入条件を記載すること。小規模は1ファイルから始められ、共通要件は必要な場合だけ別文書に置いて参照すること。 |
| REQ-SPEC-004 | 外部設計は発注者に合意が必要な UI・帳票・外部連携に限定すること。操作・状態・権限・入力制約・エラー等を含め、内部クラスは含めないこと。該当しない項目は理由付きで対象外を確認できること。 |
| REQ-SPEC-005 | 内部設計では、業務モデル、コンポーネント、ユースケース、データ・トランザクション、通信・非同期処理、エラー・認証認可、共通機能・設定、運用・移行、テスト、技術判断を変更規模に応じて整理できること。 |
| REQ-SPEC-006 | 新規開発の標準として、DDD の用語、コンテキスト、エンティティ、値オブジェクト、集約、不変条件を検討すること。プレゼンテーション、コントローラー、アプリケーション、ドメイン、インフラストラクチャの5層の責務と依存を示すこと。既存システムへ導入する場合は既存構成を尊重し、適用範囲と例外の理由・影響を提示して技術責任者の合意を得ること。小さな修正に全面的な層の再構成を暗黙に要求しないこと。 |
| REQ-SPEC-007 | 標準構成ではドメインを DB・Web フレームワーク・他層に依存させず、インフラを内側のポートの実装とすること。業務上の IF とアプリケーション固有の IF を区別すること。Web では UI と API の役割を区別し、内部 API 契約と外部公開契約の配置を判断すること。既存構成への適用範囲は REQ-SPEC-006 の合意に従うこと。 |
| REQ-SPEC-008 | 横断処理・全体設定を共通機能として整理し、AOP と適切な代替手段を比較できること。適用点・順序・例外・テストを明示し、必須の業務処理・監査を暗黙化しないこと。設定は型・必須条件・検証・環境差分等を定義すること。 |
| REQ-SPEC-009 | 全体原本を `docs/spec/current/`、変更記録を `docs/spec/changes/<変更ID>/`、議論を `docs/scratchpad/<変更ID>/` に分離すること。原本には変更後の全体像、変更記録には差分・理由・影響・原本参照と版を保存すること。 |
| REQ-SPEC-010 | 全体・フェーズ別の Scratchpad を共有できること。全体には状態、質問、決定、承認、引き継ぎ、ブランチ対応を保存し、各フェーズには検討案・レビュー指摘等を残すこと。正式成果物に未採用案を混ぜないこと。 |
| REQ-SPEC-011 | 人と AI が同じ Scratchpad を編集できること。更新前に最新版を確認し、競合時に人の変更を上書きせず差分と修復案を示すこと。通常のエディターによる変更も検知すること。 |
| REQ-SPEC-012 | 原本候補と変更記録を同じ変更ブランチで更新し、該当工程の成果物一式としてまとめて承認対象とすること。文書ごとの別承認を必須にせず、承認対象の版は REQ-WF-006 に従うこと。既定ブランチの現行原本と候補を区別し、過去版は Git の版で参照できること。終了した変更記録を現行仕様へ追従して書き換えないこと。 |
| REQ-SPEC-013 | 追加・修正では既存原本とコードの双方から互換性、移行、回帰、再承認への影響を示すこと。原本変更なしの判断も理由と参照版を記録すること。変更内容が原本へ未反映なら完了準備とはしないこと。 |

### 必要なスキル相当の手順

| 手順候補 | 期待する結果 |
| --- | --- |
| `idea-dialogue` | 課題・制約からアイデア案、比較、範囲、質問を作成 |
| `requirements-definition` | 合意したアイデアと既存仕様から、機能別の要件・受入条件を作成 |
| `external-design` | 承認済み要件から、必要な UI・帳票・外部連携の仕様を作成 |
| `ddd-internal-design` | 承認済み要件・外部設計から、内部設計と技術上の質問を作成 |
| `change-impact-analysis` | 既存仕様・コードと変更案から、影響・互換性・再承認対象を提示 |
| `canonical-spec-update` | 合意した変更を原本候補へ統合し、変更記録との対応を確認。マージは行わない |
| `consistency-review` | 原本候補・変更記録・タスク・追跡表を読み取り、不足・矛盾・未反映を提示 |

## 非機能要件

| ID | 要求 |
| --- | --- |
| NFR-SPEC-001 | 原本と変更記録を Git 管理し、マージ後も参照できること。変更記録を読み合わせなくても原本から全体の最新仕様を理解できること。 |
| NFR-SPEC-002 | 規模に応じて必要な文書だけを作成し、空の帳票・連携文書や原本の全文コピーを必須にしないこと。記録と原本の構造を機械的に揃えないこと。 |

## 受入条件

| ID | 対象 | 条件・期待結果 |
| --- | --- | --- |
| AC-SPEC-001 | REQ-SPEC-001、REQ-SPEC-002 | 壁打ちから目的・範囲・採否理由を追跡でき、要件に正常系・権限不足・入力不備・境界・外部障害の該当条件が含まれる。 |
| AC-SPEC-002 | REQ-SPEC-003、NFR-SPEC-002 | 2つの大きな機能で各文書に非機能要件と受入条件が存在し、共通内容は参照で共有される。小規模案件では1ファイルから開始できる。 |
| AC-SPEC-003 | REQ-SPEC-004 | UI のみの案件で不要な帳票・連携文書を作らず、対象外の理由を提示する。UI の権限・入力・エラー動作を発注者が確認できる。 |
| AC-SPEC-004 | REQ-SPEC-006、REQ-SPEC-007 | 新規案件の内部設計レビューで集約・不変条件・5層の責務・依存方向を確認できる。ドメインから DB 具体実装への依存案や内部 API の扱い違いを指摘できる。 |
| AC-SPEC-005 | REQ-SPEC-008 | ログ・監査・設定を設計すると、適用方法・順序・例外時の動作・検証方法・設定検証が示され、秘密の実値や隠れた業務処理を含まない。 |
| AC-SPEC-006 | REQ-SPEC-009、REQ-SPEC-010、REQ-SPEC-012、NFR-SPEC-001 | 変更前後の原本、変更差分、質問・決定・承認を別々に参照できる。原本候補と該当工程の変更記録を工程単位でまとめて承認できる。候補を現行と表示せず、過去の変更記録から対象版へ辿れる。 |
| AC-SPEC-007 | REQ-SPEC-011 | 人が Scratchpad を編集した後に古い版で AI が更新を試みると、競合を検知して停止し、人の内容が残る。 |
| AC-SPEC-008 | REQ-SPEC-013 | 追加機能の差分だけを書いた場合は原本未反映を指摘する。既存仕様を変えないバグ修正では変更なしの理由と参照版を残せる。 |
| AC-SPEC-009 | REQ-SPEC-005 | データ更新と外部通信のある案件で、データ構造、整合性、トランザクション、通信・非同期処理の該当設計を確認できる。必要な項目が欠落する場合は内部設計の不足として提示する。 |
| AC-SPEC-010 | REQ-SPEC-005 | 権限や障害対応のある案件で、エラー分類、認証認可、運用・移行の該当設計を確認できる。適用しない項目には理由があり、必須事項が未確定なら承認へ進めない。 |
| AC-SPEC-011 | REQ-SPEC-005 | 内部設計から、ユースケース・コンポーネント・共通機能と要件の対応、テスト方針、重要な技術選択の理由・代替案を確認できる。変更規模に関係しない設計の全面再生成を要求しない。 |
| AC-SPEC-012 | REQ-SPEC-006、REQ-SPEC-007 | 5層でない既存システムへの小さな修正で、既存構成、適用範囲、例外の理由・影響・合意を記録できる。合意していない全面的な再構成をタスクへ追加しない。 |
