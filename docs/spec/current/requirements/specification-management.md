# 仕様・設計・Scratchpad 管理の要求

## 目的・対象範囲

議論、変更単位の記録、システム全体の原本を分離し、合意した内容を次工程へ引き継ぐ。要件・外部設計・内部設計の作成支援と、追加・修正時の影響分析を含む。

状態: 要求定義ドラフト。

出典: [docs/idea/intial-idea.md](../../../idea/intial-idea.md) 第4・5・7・10・12章。共通要求: [common.md](common.md)。

| REQ-SPEC-014 | CAT-AUTHOR 仕様作成 | FUN-SPEC-005、FUN-SPEC-007 | 内部設計の技術判断のうち、複数の候補があり後から変えにくいものを設計判断記録（ADR）として案件中に起票できること。起票は推奨で必須ではない。ADR は背景、決定、選択肢と不採用理由、影響、状態、置換関係を持ち、内部設計の工程成果物として技術責任者の工程承認を受けて初めて採用（Accepted）と扱うこと。承認済みの ADR を原本へ正式番号で反映し、反映後は書き換えず新しい ADR で置き換えること。既存原本の暗黙の判断を遡って起票しないこと。ADR のために新しい承認工程や承認役割を追加しないこと。 |

## 非機能要件

| ID | 要求 |
| --- | --- |
| NFR-SPEC-001 | 原本と変更記録を Git 管理し、マージ後も参照できること。変更記録を読み合わせなくても原本から全体の最新仕様を理解できること。 |
| NFR-SPEC-002 | 規模に応じて必要な文書だけを作成し、空の帳票・連携文書や原本の全文コピーを必須にしないこと。記録と原本の構造を機械的に揃えないこと。 |

| AC-SPEC-007 | REQ-SPEC-011 | 人が Scratchpad を編集した後に古い版で AI が更新を試みると、競合を検知して停止し、人の内容が残る。 |
| AC-SPEC-008 | REQ-SPEC-013 | 追加機能の差分だけを書いた場合は原本未反映を指摘する。既存仕様を変えないバグ修正では変更なしの理由と参照版を残せる。 |
| AC-SPEC-009 | REQ-SPEC-005 | データ更新と外部通信のある案件で、データ構造、整合性、トランザクション、通信・非同期処理の該当設計を確認できる。必要な項目が欠落する場合は内部設計の不足として提示する。 |
| AC-SPEC-010 | REQ-SPEC-005 | 権限や障害対応のある案件で、エラー分類、認証認可、運用・移行の該当設計を確認できる。適用しない項目には理由があり、必須事項が未確定なら承認へ進めない。 |
| AC-SPEC-011 | REQ-SPEC-005 | 内部設計から、ユースケース・コンポーネント・共通機能と要件の対応、テスト方針、重要な技術選択の理由・代替案を確認できる。変更規模に関係しない設計の全面再生成を要求しない。 |
