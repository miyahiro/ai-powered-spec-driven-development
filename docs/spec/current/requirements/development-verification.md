# 開発・テスト・検証の要求

## 目的・対象範囲

承認済み要件・設計をタスクへ分解し、TDD と独立レビューで実装を検証する。実施済み・未実施の証拠を残し、追加・修正と仕様変更にも対応する。

状態: 要求定義ドラフト。

出典: [docs/idea/intial-idea.md](../../../idea/intial-idea.md) 第2・3・7・10・12章。共通要求: [common.md](common.md)。

## 機能要件・業務ルール

| ID | 要求 |
| --- | --- |
| REQ-DEV-001 | 承認済み設計から依存順のタスクを作り、要件・設計 ID、編集範囲、入力、担当、テスト方法、実行環境、完了条件を明示すること。新しい要件をタスク担当の判断だけで追加しないこと。 |
| REQ-DEV-002 | 振る舞いを追加・変更する実装タスクは、期待動作のテストを先に作り、意図した理由で失敗する Red、最小実装で成功する Green、振る舞いを保つ Refactor と再検証を行うこと。構文・環境エラーを仕様上の Red と扱わないこと。振る舞いの実装を伴わない文書更新・初期設定・環境構築等は、構文・設定検証・レビュー等の適切な確認方法と完了条件を定め、無理に Red を作らないこと。 |
| REQ-DEV-003 | ドメインの単体、インフラの統合、境界の契約、利用シナリオの E2E、非機能の検証を必要に応じ計画すること。UI 視覚確認、運用手順、探索的・手動検証は確認者・手順・証跡を定めること。 |
| REQ-DEV-004 | 実装前に要件・設計・タスクの不足・矛盾をレビューし、実装後にコード・テストと受入条件を照合すること。レビュー担当は読み取り専用で結果を返し、修正や追加タスクは案として提示すること。結果の保存は REQ-WF-010 に従い、オーケストレーターが人と合意した範囲で行うこと。 |
| REQ-DEV-005 | 検証の対象コミットまたは内容ハッシュ、環境、日時、方法、結果を記録すること。自動検証ではコマンド・終了コード、手動検証では確認者・手順・観測結果・必要な証跡を記録し、存在しないコマンド・終了コードを必須にしないこと。未実施・失敗・実行不能・検証対象外と理由、必要な次の操作を区別し、未検証を成功と扱わないこと。完了判断は共通要求で定めた検証対象について行うこと。 |
| REQ-DEV-006 | 全体原本の要件・設計と現行テスト、変更記録の要件・設計とタスク・実行証跡を追跡できること。参照が存在するだけで要件を満たしたと判断しないこと。 |
| REQ-DEV-007 | バグ修正では期待動作と現象を確認し、現象を再現する回帰テストを修正前に作ること。追加・修正では影響する既存動作を回帰検証すること。 |
| REQ-DEV-008 | 実装中の仕様変更は影響する作業を止め、要件・設計・原本・承認・タスクの見直しへ戻すこと。作業中コードや完了履歴を破棄せず、変更・追加・不要化・再検証するタスクを示すこと。 |
| REQ-DEV-009 | 必要な受入確認と品質基準を満たした結果を技術責任者へ提示すること。完了承認を受けても push・PR・マージ・本番反映の許可を得たとは扱わないこと。 |

### 必要なスキル相当の手順

| 手順候補 | 期待する結果 |
| --- | --- |
| `task-planning` | 承認済み設計から依存順のタスクを作成し、実装は TDD、それ以外は適切な確認方法を割り当てる |
| `tdd-cycle` | 許可された実装タスク単位でテスト先行実装、再検証、証跡の更新を実行 |
| `verification-and-review` | 実装・受入条件・結果を照合し、指摘、未実施、残課題、追加タスク案を提示 |

## 非機能要件

| ID | 要求 |
| --- | --- |
| NFR-DEV-001 | 検証証跡から対象版と実施条件を特定できること。コードや仕様が変わった後に古い成功結果を現行の成功として流用しないこと。 |
| NFR-DEV-002 | 実装担当の自己評価や同じ担当の役割名変更だけで独立レビューを完了としないこと。独立レビューの主体・記録・人による代替は REQ-WF-011 に従うこと。別役割のレビューでも人の承認を代行しないこと。指摘を消す目的で受入条件やテストを勝手に弱めないこと。 |

## 受入条件

| ID | 対象 | 条件・期待結果 |
| --- | --- | --- |
| AC-DEV-001 | REQ-DEV-001、REQ-DEV-004 | 設計に対応しないタスクや検証方法のないタスクを渡すと、実装前に不足を指摘し、要件・設計の見直しへ案内する。 |
| AC-DEV-002 | REQ-DEV-002 | 振る舞いを変更する1実装タスクで、意図した失敗、最小実装後の成功、リファクタリング後の成功を確認できる。環境エラーの失敗記録だけで Red 完了にはならない。 |
| AC-DEV-003 | REQ-DEV-003、REQ-DEV-005 | 自動・手動の必要な検証項目に、手順と担当がある。自動検証はコマンド・終了コード、UI の目視確認は確認者・手順・観測結果を記録し、後者に架空のコマンドを要求しない。環境不足で必要な統合テストを実行できない場合は未実施と記録し、完了を提示しない。共通要求で検証対象外とした役割の並行実行・MCP 連携は、対象外と記録して完了の必須条件にしない。 |
| AC-DEV-004 | REQ-DEV-004、REQ-DEV-006、NFR-DEV-002 | 要件に未対応のコードやテストをレビューで指摘し、追加タスク案を返す。レビュー依頼だけではコード・タスク・承認状態を変更しない。 |
| AC-DEV-005 | REQ-DEV-005、REQ-DEV-006、NFR-DEV-001 | 要件からタスク・テスト・証跡・対象版へ辿れる。コード変更後に旧版の結果を参照すると、再検証が必要と表示する。 |
| AC-DEV-006 | REQ-DEV-007 | バグを再現するテストが修正前に失敗し、修正後に成功する。元の現象と関連する回帰結果を確認できる。 |
| AC-DEV-007 | REQ-DEV-008 | 実装中の仕様変更で影響タスクを止め、作業中コードを保持する。再承認とタスク更新後に再開し、影響した完了タスクも再検証する。 |
| AC-DEV-008 | REQ-DEV-009、NFR-DEV-002 | 実装担当が「完了」と返しても人の完了承認を要求する。完了承認後にも、未許可の push・マージ・本番反映を実行しない。 |
| AC-DEV-009 | REQ-DEV-001、REQ-DEV-002 | 振る舞いの実装を伴わない文書更新・初期設定タスクには、レビューや設定検証などの方法と完了条件を割り当てられる。失敗テストがないことだけで作業を阻害せず、確認未実施なら完了にはしない。 |
| AC-DEV-010 | REQ-DEV-004 | 読み取り専用担当がレビュー結果を返し、保存の依頼を受けたオーケストレーターが記録する。結果の保存だけでは追加タスクを実行せず、元のコード・承認を変更しない。 |
