# 仕様・成果物・状態管理設計

状態: 設計ドラフト。入力: [仕様管理要求](../requirements/specification-management.md)。工程: [ワークフロー設計](workflow-orchestration.md)。

## DES-SPEC-001 保存先と原本

正式成果物は Markdown、機械的に確認する状態は JSON とする。Markdown は人と AI が編集し、JSON も人が確認・編集できるが、再開時にスキーマと参照を検証する。状態専用サーバーやデータベースは導入しない。

```text
docs/
  spec/
    current/
      requirements/                 # 機能別要件・共通要求
      design/                       # 対象に応じた外部・内部設計
    changes/<change-id>/
      change.md                     # 種別・目的・差分・理由・影響・参照版
      <phase>.md                    # 必要な工程の変更内容だけ
      tasks.json                    # 依存順タスクと完了条件
      traceability.json             # 要件・設計・タスク・テスト・証跡の対応
      verification/                 # 結果・手動確認・レビュー
  scratchpad/<change-id>/
    overview.md                     # 質問・決定・現在地の人向け記録
    <phase>.md                      # 必要な工程だけ作成する検討板
    state.json                      # 状態・質問・決定・承認・許可・版
    operations.json                 # 登録・状態遷移の操作 ID と確定結果
    pending/                        # 中断した更新の復旧情報。通常は空
```

パスは設計上の配置例であり、今回これらの案件ファイルを作成しない。空の工程文書や原本の全文コピーは作らない。小規模案件の要件は1ファイルでよく、外部設計の対象がなければ理由を変更記録へ残す。

既定ブランチの `current` を現行原本、変更ブランチの `current` を原本候補として表示する。「現行」は公開・本番反映済みを意味しない。変更記録には当該案件の差分と参照版だけを残し、完了後の案件を新しい原本に追従させて書き換えない。

変更 ID は `CHG-0001` 形式の連番を候補に既存記録で重複確認する。ブランチ名からパスを直接生成しない。ブランチ・基点コミット・既定ブランチを状態へ明示し、存在しない Git 情報は `null` とする。複数候補がある受付では人に案件を選んでもらう。

## DES-SPEC-002 成果物の作成規約

| 工程 | 正式成果物に含める項目 | 原本・変更記録への反映 |
| --- | --- | --- |
| アイデア | 課題・利用者・価値・候補比較・採否・対象範囲・対象外 | 採用案は案件のアイデア成果物、検討中の案は Scratchpad |
| 要求定義 | 目的・シナリオ・機能・業務ルール・データの意味・権限・制約・依存・非機能・受入条件 | 機能別の原本に統合し、変更した ID・理由・影響を記録 |
| 外部設計 | UI の状態・操作・入力・権限・エラー、帳票、外部連携契約 | 発注者との合意に必要なものだけ原本化。内部クラスは含めない |
| 内部設計 | 業務モデル・構成・ユースケース・データ・トランザクション・通信・非同期・エラー・認証認可・共通機能・設定・運用・移行・テスト・技術判断 | 変更規模に必要な項目を設計し、対象外の理由と判断根拠を明示 |

機能・非機能・受入条件は機能文書内へまとめ、共通事項は参照する。要求 ID は移動で変えず、設計 ID `DES-<機能>-<番号>` と要件の対応を各設計に記録する。採否未確定の案や未解決質問を、確定した正式仕様の文章として混ぜない。

新規の支援先アプリでは DDD の5層を標準とする。プレゼンテーションは UI、コントローラーは API 境界、アプリケーションはユースケース・認可適用・トランザクションの調整、ドメインは業務モデル・不変条件・業務ポート、インフラストラクチャは内側のポートの実装を担う。ドメインは他層・DB 実装・Web フレームワークへ依存しない。業務リポジトリ IF とユースケース固有のサービス IF を区別する。

既存構成では全面再設計を暗黙に要求せず、適用範囲・例外・理由・影響を技術責任者に合意してもらう。内部 API と外部公開 API の契約を区別し、公開互換性を設計する。横断処理は AOP・middleware・interceptor・decorator を比較し、必要な業務処理・監査は暗黙に隠さない。設定には型・必須条件・検証・環境差分を持たせ、秘密の実値は書かない。

## DES-SPEC-003 状態の形式

`state.json` の `schemaVersion` は `1` とする。JSON Schema Draft 2020-12 による形式定義と、工程・承認・参照の意味的な検査を分離する。補助機能に同梱するスキーマは導入先の案件 ID・絶対パスを含めない。

| フィールド | 内容・制約 |
| --- | --- |
| `schemaVersion` | 形式の版。未対応版を自動書き換えしない |
| `changeId`, `kind`, `purpose`, `scope` | 変更単位、種別、目的・対象と対象外 |
| `git` | `defaultBranch`, `branch`, `baseCommit`。Git 準備前は未登録 |
| `phase`, `status` | ワークフロー設計の列挙値。中断には `resumeStatus` も保存 |
| `actors` | 発注者・技術責任者、代理記録者の名前と役割。兼任可 |
| `questions` | ID、質問・選択肢・推奨・影響、期限工程、状態、回答・出所・反映先 |
| `decisions` | ID、判断・根拠、関連質問、正式成果物・対象版の参照 |
| `approvals` | 工程、対象一覧・版、承認役割・回答者・代理記録者、日時・判断・回答出所 |
| `permissions` | 案件・操作種別・編集先・読み取り先・生成先・コマンドプロファイル・外部操作先、回答出所・有効範囲 |
| `phaseManifests` | 工程ごとの成果物集合、参照した入力版、計算した版 |
| `handoff` | 最後の確定操作、次作業、未解決・未実施の参照、中断理由 |
| `integration` | 開発完了、Git 操作許可、マージ先コミット、本番反映の別々の記録 |

追加フィールドはスキーマ更新で管理する。パスは workspace 相対の POSIX 表記とし、URI・`..`・未許可の絶対パスを案件の編集先として受け付けない。日時は UTC の ISO 8601 とする。秘密の回答は値を保存せず、設定済みか否かと必要な参照だけを記録する。

Scratchpad の Markdown は人向けの議論と手動回答の入力であり、JSON は検査した状態の根拠である。人が Markdown に回答を追記した場合は未取り込みとし、AI が意味・出所・影響を確認して JSON と正式成果物へ反映する。「承認」と書いてあるだけで工程承認にしない。人が JSON を編集した場合も形式検査、回答の出所、成果物の版との一致を確認する。

## DES-SPEC-004 リビジョンと工程承認

文書更新用のリビジョンは、各ファイルのバイト列の SHA-256 とする。新規ファイルには期待版 `null` を用い、既存ファイルの存在を上書き許可と誤認しない。

工程承認用の版は、対象ファイルの相対パスと SHA-256 の一覧をパス順に並べた正規化 JSON の SHA-256 とする。承認前に対象一覧を人へ提示する。単一の Git コミットだけでは未コミット変更を識別できないため、ファイル内容の版を使用する。

| 工程 | 承認対象の集合 |
| --- | --- |
| アイデア | 採用した案件アイデア文書と当該工程の変更内容 |
| 要求定義 | 要件原本候補一式と当該工程の変更内容 |
| 外部設計 | 該当する外部設計原本候補と当該工程の変更内容。不要なら対象外判断の記録 |
| 内部設計 | 該当する内部設計原本候補と当該工程の変更内容 |
| 開発完了 | タスク・追跡表・必要な実装とテスト・検証結果・独立レビュー結果 |

対象集合は工程の成果物ルートと一覧で管理し、承認後に該当文書が追加・削除された場合も再計算する。入力となる前工程の版も保存し、前工程変更時には後続の影響を確認する。実装・テストの集合はタスクの編集範囲と依存関係から決め、無関係なファイルを無条件に含めない。

`state.json`、`operations.json`、`pending/`、承認回答、進行状態、質問板は工程承認の対象から除外する。承認記録の追加で対象版を変更しない。質問板の回答で正式成果物を変更した場合は、成果物の版が変わるので影響する工程の承認を取り直す。除外は改ざん防止の保証ではなく、運用上の循環を防ぐための区分である。

承認の記録順は、対象集合を計算、工程と対象版を提示、人の明示回答を取得、版を再照合、回答者・役割・出所・代理記録者を保存、である。人が回答した時点から成果物が変わっていれば旧版承認として保存し、現在版は承認待ちとする。「続けて」、ツール許可、質問への回答は工程承認へ変換しない。

## DES-SPEC-005 更新・競合・復旧

管理下の更新は[ツール設計](tool-integration.md)のランナーへ集約する。通常の文書差分には操作 ID を必須にせず、再送され得る質問・決定登録・状態遷移だけに操作 ID を使用する。

1. 変更 ID・ブランチ・対象範囲・期待版を確認する。
2. workspace 単位の短時間の更新ロックを取得し、期待版を再照合する。
3. 形式・参照・変更内容を検証し、途中更新を検出するため `pending/` へ対象と旧版・新版を保存する。
4. 同じファイルシステム上の一時ファイルに新内容を書き、ファイル単位で置換する。
5. 対象全件の新版を再確認し、登録操作なら `operations.json` に操作 ID・入力のハッシュ・結果を確定する。
6. 復旧情報を完了扱いにし、ロックを解放する。

ロックは管理下の更新同士にだけ有効であり、通常のエディターの手動編集を排他したとは扱わない。手動編集が疑われる場合は差分を示して停止し、編集を区切ってもらってから再照合する。競合解消のために人の内容を自動削除しない。

複数ファイルの置換を単一の原子的更新と呼ばない。中断後は `pending/` の旧版・新版と実ファイルを照合し、全件適用済み、未適用、部分適用、別の手動変更を区別する。部分適用や状態不明が残る間は工程移行を止め、人と合意して残りの適用または修復を行う。無条件のロールバックはしない。

同じ操作 ID と同じ入力の再送は保存した結果を返し、同じ操作 ID で入力が違えば衝突として拒否する。永続記録を結果返却より先に確定し、再起動で記憶を失っても二重登録しない。復旧情報と確定結果は案件内のファイルとして残し、隠れたサーバーだけを根拠にしない。

## DES-SPEC-006 追加・修正・再開

追加・修正は基点の原本と現在コードを読み、互換性・データ移行・回帰・依存先・再承認の影響を整理する。原本変更なしの修正でも理由と参照版を変更記録へ残す。差分だけの記録では原本への統合を完了扱いにしない。

再開は、案件選択、保存形式、ブランチ・基点、未完了更新、手動変更、工程承認の版、質問と期限、タスク・検証の版、許可範囲の順に照合する。Git 準備前の壁打ちは未登録状態のまま再開できる。正式な変更管理中のブランチ不一致は関連作業を停止する。

状態・タスク等の手動変更は以前の版との差分を見て確認する。既定ブランチの原本が更新されていれば影響と必要な再検証・再承認を提示する。状態が合うという理由だけで過去の成功証跡を流用しない。
