# ワークフロー・エージェント・スキル設計

入力: [ワークフロー要件](../requirements/workflow-orchestration.md)。共通方針: [README.md](README.md)。

## DES-WF-001 対話と工程

外部インターフェースは Copilot Chat の対話である。以下は入力例で、固定のコマンドではない。

| 利用者の意図 | 窓口の処理 | 応答 |
| --- | --- | --- |
| 新しく始めたい／〜を作りたい／〜を考えたい／〜を直したい（始める意思や相談） | 受付（DES-WF-003 `sdd-change-intake`） | 変更 ID・規模の推奨・承認者・ブランチ名の確認 |
| 状況を教えて | `status.md` と検査スクリプトの要約だけを読む | 工程・状態・期限の来た質問・承認待ち・再承認が必要な工程・タスク・次の作業 |
| 承認します（または確認フォームの「承認する」） | 対象を示した後の回答か、回答者が承認者かを確かめる | 承認のコミットと、次の作業の提示 |
| 要件をまとめて／設計を進めて／続けて | `status.md` の `phase` と承認を確かめ、次の工程を始める | その工程の成果物と、必要な質問 |
| 止めて／再開して／要件に戻して | 意図を確かめて `status.md` を更新する | 中断・再開・差し戻しの結果と次の作業 |
| この要件を深掘りして（grill-me） | 深掘り（DES-WF-003 `sdd-grill-me`） | 1問ずつの質問と推奨、記録した答え |
| この設計書をレビューして | レビュー担当に読み取り専用で依頼する | 指摘と修正案だけ |
| 承認はどう答えればいい？（使い方の質問） | ガイド（DES-WF-007 `sdd-guide` の使い方の回答） | ユーザーガイドを根拠にした短い答えと根拠の節。答えがなければ分からないこと |
| 次は何をすればいい？ | ガイド（DES-WF-007 の次の作業の案内） | 今の工程と状態、次の作業、依頼の言い方、必要な判断。案件がなければ受付の始め方 |
| 手引きして／手引きはもういい | ガイド（DES-WF-007 の伴走の開始・停止） | 伴走の記録の追加・削除と、今の位置・次の依頼の言い方 |
| 〜を開発して／作って／実装して（成果物を作る作業そのものの依頼で、案件がない、または前の工程の承認がない） | 受付も工程の作業も始めず、ガイド（DES-WF-007 の工程の説明）で答える | 規模に応じた工程の流れ、今どの工程から始めるべきか、その工程を始める依頼の言い方、他のブランチの進行中の案件（あれば） |

- 受付の依頼と工程の作業の依頼は、言い方の一覧ではなく依頼の中身で分ける。始める意思や相談（「〜したい」「〜を考えたい」「新しく始めて」）は受付の依頼、成果物を作ること自体の指示（「〜を開発して」「〜を作って」「〜を実装して」）は工程の作業の依頼とする。作る対象が依頼に書かれていても、工程の作業の依頼は受付の依頼として扱わない（DES-WF-007 の「工程に沿わない依頼」）。

工程と承認は規模で決まる。

| 規模 | 工程（`phase` の値） | 承認（ゲート） |
| --- | --- | --- |
| 標準 | `ideation` → `requirements` → `design` → `implementation` → `done` | `requirements`、`design`、`completion` |
| 軽量 | `outline` → `implementation` → `done` | `outline`、`completion` |

- 工程の区切り（受付の後、壁打ちの合意の後、工程の承認の後）では、`status.md` に次の作業を書き、それを示して止まる。次の工程は人の依頼で始める。依頼の言い方は問わず、「続けて」も依頼として扱う（承認にはならない）。
- 壁打ち（`ideation`）には承認を置かない。結果は要件の承認でまとめて確かめる。
- 軽量の「要点」（`outline`）では、原本の要件を差分で直接更新し、設計の要点を `docs/spec/changes/<ID>/outline.md` に数行で書く。両方を1回で承認する。
- 外部設計・内部設計は標準の `design` で一緒に承認する。外部設計が不要なら、理由を内部設計の文書か `status.md` に1行残す。
- 規模の変更と前の工程への差し戻しは人の確認を得て `status.md` を更新する。差し戻した工程以降の承認は、再承認が必要として扱う。

進行状態（`state`）は `active`（作業中）、`waiting-approval`（承認待ち）、`blocked`（期限の来た質問などで止まっている）、`paused`（中断）、`done`（完了）とする。

## DES-WF-002 エージェント構成

| 設定 | 責務 | tools | 備考 |
| --- | --- | --- | --- |
| `sdd-orchestrator.agent.md` | 窓口。受付、壁打ち、要件・要点、質問、承認とコミット、`status.md`、状況確認、委任、ガイド（`sdd-guide` を使う） | `read`、`search`、`edit`、`execute`、`agent`、`vscode_askQuestions` | 利用者が選ぶのはこれだけ（`user-invocable: true`）。呼べる担当は下の3つ |
| `sdd-designer.agent.md` | 外部設計、内部設計、ADR | `read`、`search`、`edit` | `user-invocable: false` |
| `sdd-implementer.agent.md` | タスク分解、テスト先行の実装、確認の記録 | `read`、`search`、`edit`、`execute` | `user-invocable: false` |
| `sdd-reviewer.agent.md` | 仕様と実装の独立レビュー | `read`、`search` | 書き込みもターミナルも使わない |

- 4つのエージェントは、本文の冒頭で作業の前に共通ルール（`plugins/sdd/common-rules.md`）を読む（DES-TOOL-001）。
- hook は付けない。ツールの実行と編集はホストの標準の確認に従う。
- 承認とコミットは窓口だけが行う。担当はコミットしない。
- モデルは固定しない。
- ガイドのための専用のエージェントは作らない。ガイドは窓口が `sdd-guide` スキルで行う（人が話す相手を窓口の1つに保つ。DES-WF-007）。

## DES-WF-003 スキル構成

スキルはプラグインの `skills/<name>/SKILL.md` に置き、各スキルは「入力」「手順」「停止」「出力」を持つ。テンプレートは該当スキルの `templates/` に置き、**新しい文書を作るときだけ** 読む。

| スキル | 使う場面 | 主な出力 |
| --- | --- | --- |
| `sdd-change-intake` | 新規・改善・修正の受付 | 変更 ID、規模、承認者、`status.md`、確認後のブランチ |
| `sdd-workflow-status` | 状況確認、記録の一覧、再開 | 要約による状況、再開の可否 |
| `sdd-clarification` | 質問の整理と回答の反映 | `status.md` の質問の表、成果物への反映 |
| `sdd-grill-me` | 承認の前の深掘り（任意） | 1問ずつの質問、`sdd-clarification` と同じ形の記録と反映 |
| `sdd-phase-approval` | 承認の依頼と承認のコミット | 承認の行、承認のコミット、次の工程 |
| `sdd-idea-dialogue` | 壁打ち | `idea.md`（必要な場合） |
| `sdd-requirements-definition` | 要件、軽量の要点 | 原本の要件、`outline.md` |
| `sdd-external-design` | 外部設計 | 原本の外部設計（または省略の理由） |
| `sdd-ddd-internal-design` | 内部設計、ADR | 原本の内部設計、ADR 案 |
| `sdd-change-impact-analysis` | 追加・修正の影響の調査 | 影響の一覧（応答だけ） |
| `sdd-task-planning` | タスク分解 | `tasks.md` |
| `sdd-tdd-cycle` | テスト先行の実装 | コード・テスト、`tasks.md` の結果 |
| `sdd-review` | 仕様・実装のレビュー | 指摘（応答だけ） |
| `sdd-spec-check` | 仕様と案件の検査、案件の状況の要約（他のスキル・窓口から参照） | 検査の結果、要約（応答だけ） |
| `sdd-guide` | 使い方の回答、次の作業の案内、伴走の開始・停止と案内、工程に沿わない依頼での工程の説明（DES-WF-007） | 応答だけ。伴走の開始・停止のときだけ `status.md` の `guide` の行 |

深掘り（`sdd-grill-me`）は窓口が行う（確認フォームと編集が要るため）。判断の分かれ道を前提の順に1問ずつ、推奨付きで聞き、原本やコードで分かることは調べて示す。答えの記録と反映は `sdd-clarification` の手順を使う。10問程度ごとに続けるかを聞き、人が止めたら止める。承認の条件にはしない。

## DES-WF-004 承認とコミット

1. 要件・設計・要点の承認を求める前に、その工程でまだ深掘りをしていなければ、一度だけ提案する。断られたら、そのまま承認へ進む。完了の承認では提案しない。
2. 窓口が工程の成果物の一覧（`git status --short` と `git diff --stat` から作る）と変更の要点を示し、確認フォーム（`vscode_askQuestions`）で「承認する／修正する」を聞く。自由入力では「承認します」「この工程を承認します」など明確な肯定だけを承認とする。
3. 回答者が `status.md` の `approvers` にいるかを確かめる。曖昧・条件付きの回答、対象を示す前の回答は聞き直す。
4. `status.md` の承認の表に行を追加する（工程・日時・承認者・対象のパス）。`state` を次の工程の `active` にし、`phase` を進める。
5. 対象のパスと `status.md` だけを `git add -- <パス>` で指定し、次のメッセージでコミットする。

```text
approve(<gate>): <変更ID> <題名>

承認者: <名前>
対象: <パス>, <パス>
```

6. コミットのハッシュと次の作業を応答で示して止まる。次の工程は人の依頼を受けてから始める。

承認後に対象が変わったかは、検査スクリプトが「その承認のコミット」と「今の作業ツリー」の差分を対象のパスについて取って判定する（DES-TOOL-003）。変わっていれば、その工程は再承認が必要として示す。

工程の承認は、次の工程の範囲（`status.md` の範囲と設計に書いたパス）での編集・ローカルのテスト・作業の区切りのコミット（`chg(<変更ID>): <要点>`）の許可を兼ねる。範囲外の変更・削除・新しい依存の追加は、その都度聞く。push・PR・マージは行わず、手順を案内する。

## DES-WF-005 委任と返却

委任はパスと要点だけで行い、文書の本文・要約・会話全文を渡さない。

```text
変更 ID: CHG-0001 / 工程: design / ブランチ: change/CHG-0001
読むもの: docs/spec/current/requirements/inquiry.md の REQ-INQ-003〜005
編集してよい範囲: docs/spec/current/design/
作業メモ: docs/spec/changes/CHG-0001/note.md
制約: 承認しない・コミットしない
返却: 変更したファイル、要点（数行）、メモに追記したこと、質問
```

返却を受けた窓口は、文書を読み直さずに `git status --short` と `git diff --stat` で、変更されたファイルが返却と一致し、範囲内にあることを確かめる。食い違えば返却を採用しない。内容の確認はレビュー担当と人の承認で行う。

担当は会話の文脈を引き継がないため、作業で分かった知識は作業メモ `docs/spec/changes/<変更ID>/note.md` に残し、次の担当や別の会話で同じ調査をやり直さないようにする。

- 書くもの: 調べて分かった事実（出典のパス付き）、作業上の前提、試してうまくいかなかったこと、テストや起動の方法。節は「分かったこと」「前提」「うまくいかなかったこと」「テスト・起動」とし、各項目を数行の箇条書きにする。
- 書かないもの: 決定事項（質問の表・原本・ADR に書く）、原本の写し、秘密の値。
- 承認の対象にしない。最初に書く担当が作り、既存の項目は差分で直す。古くなった項目は消すか直す。
- 窓口は委任でメモのパスを渡し、自分で調べたことも書く。設計担当と実装担当は必要な節だけを読み、分かったことを追記して、返却の要点に追記したことを書く。レビュー担当は読むだけで、書き残すべき事実があれば返却に含める。
- 作業の区切りのコミットや承認のコミットには、変更があればメモも含める。

## DES-WF-006 状況確認・中断・再開

- 状況確認: `sdd-spec-check` スキル（DES-WF-003）で検査スクリプトを変更 ID 付きで実行し、その要約と `status.md` だけで答える。成果物を個別に読まない。
- 中断: `state` を `paused` にし、「次の作業」に再開する地点を書く。作業中のコードがあれば `chg(<変更ID>): 中断時点` としてコミットするかを聞く。
- 再開: 検査スクリプトの要約で、ブランチ、再承認が必要な工程、期限の来た質問を確かめる。不一致がなければ `state` を戻して続ける。今のブランチにその案件の `status.md` がなければ、検査スクリプトが案件のあるローカルのブランチを示す（DES-TOOL-003）。窓口は確認を得てからそのブランチに切り替え、切り替えた後の要約で確かめる。

## DES-WF-007 ガイド（sdd-guide）

使い方と工程の案内は、スキル `sdd-guide` が受け持つ。窓口の依頼表から読み、利用者が `/sdd-guide` で直接呼ぶこともできる（`user-invocable: true`）。専用のエージェントは作らない。案内だけを行い、工程の作業は窓口が行う。

### 配置と参照

- 置き場所: `plugins/sdd/skills/sdd-guide/SKILL.md`。テンプレートとスクリプトは持たない。
- 参照は相対リンクで書き、リポジトリ版では書き出しのときに書き換わる（DES-TOOL-001・007）: ユーザーガイド `../../user_guide.md`、検査 `../sdd-spec-check/SKILL.md`、共通ルール `../../common-rules.md`、導入・管理ガイド `../../README.md`。
- ユーザーガイドの内容（工程の説明、承認の答え方、依頼の例など）をスキルに写さない。スキルが持つのは、どの場面でユーザーガイドのどの節を読むか（下の表）と、答えの形だけとする（NFR-WF-004）。依頼の言い方もユーザーガイドの依頼の例から引く。ユーザーガイドは、工程の区切りごと（受付の後、壁打ちの合意の後、各工程の承認の後、完了）に依頼の例を持つ。
- 直接呼ばれたときは共通ルールを読まないため（DES-TOOL-001）、スキルの手順に「ファイルを変えるのは伴走の記録の1行だけ」「工程を始めない」「承認しない」を書く。

### 手順

入力の言葉から、次の5つのどれかを選ぶ。選べなければ、どれを求めているかを1問で聞く。

| 場面 | 読むもの | 手順 | 出力 | 書き込み |
| --- | --- | --- | --- | --- |
| 使い方の回答（REQ-WF-014） | `user_guide.md` の目次、該当する節だけ | 目次から節を選んで読み、その記述だけで答える。根拠になる記述がなければ推測で答えず、「ユーザーガイドには見当たらない」と伝え、「詳しく調べて」と頼めば関係する文書まで見ることを1行添える | 数行の答えと、根拠の節へのリンク | なし |
| 詳しく調べて（REQ-WF-014） | 導入・管理ガイド、共通ルール、エージェント・スキルの定義のうち関係する節だけ | 頼まれたときだけ読む。案件の成果物とコードは読まない。それでも答えがなければ、分からないと伝える | 答えと、根拠の文書のパス | なし |
| 次の作業の案内（REQ-WF-015） | `sdd-spec-check` の要約（変更 ID 付き）、必要なら `status.md`、ユーザーガイドの依頼の例の節。案件が決まらないときは、変更 ID なしの検査の「他のブランチの進行中の案件」 | 変更 ID は今のブランチ（`change/<ID>`）から推す。決まらなければ、今のブランチの `docs/spec/changes/` で `state` が `done` でない案件と、他のブランチの進行中の案件（DES-TOOL-003）を候補として示し、選んでもらう。他のブランチの案件が選ばれたら、一覧の工程・状態とブランチ名を示し、「<変更ID> を再開して」と頼めば窓口が確認してから切り替えることを案内する（自分では切り替えない）。成果物は個別に読まない。候補がなければ受付の始め方を示す | 今の工程と状態、次の作業、それを始める依頼の言い方、必要な判断（承認・期限の来た質問・再承認・ブランチの不一致） | なし |
| 伴走の開始・停止（REQ-WF-016） | `status.md` の front matter | 開始: 案件があれば `guide: on` の行を差分で加え、「伴走の案内」を返す。案件がなければ受付の始め方を示し、続けて受付をしたら、受付（`sdd-change-intake`）が `status.md` を作るときに `guide: on` を入れる（下の「受付での伴走の開始」）。停止: `guide` の行を消し、以後は案内を添えないことを伝える | 開始・停止の結果と、今の位置・次の依頼の言い方 | `status.md` の `guide` の行だけ |
| 工程の説明（REQ-WF-017） | `sdd-spec-check` の要約（案件があれば）。案件がなければ変更 ID なしの検査の「他のブランチの進行中の案件」。ユーザーガイドの規模と全体の流れの節 | 窓口が工程に沿わない依頼と判定したときに読む（下の「工程に沿わない依頼」）。作業は始めない | 規模ごとの工程の流れ（節へのリンクと数行）、今どの工程から始めるべきか、残りの承認、その工程を始める依頼の言い方 | なし |

伴走の案内（伴走中に工程の区切りの応答へ添えるもの）は3行以内とする（NFR-WF-003）。

```text
手引き: 今は <工程>（<状態>）です。
次は「<依頼の言い方>」と頼んでください。
あなたの判断: <承認・質問への回答など。なければ「なし」>
```

- 区切りの直後は窓口が `status.md` を更新したばかりなので、その `phase`・`state`・承認・次の作業から作り、検査スクリプトをもう一度実行しない。依頼の言い方はユーザーガイドの該当する節から引く。

停止: 案件を選べない。使い方の回答で、ユーザーガイドを読めない。

### 伴走の記録

伴走していることは、`status.md` の front matter の任意の項目 `guide` に書く（書式は DES-SPEC-003、検査は DES-TOOL-003）。

```markdown
---
id: CHG-0001
...
branch: change/CHG-0001
guide: on
---
```

- 値は `on` だけとし、伴走していないときは行を置かない（`off` を書かない）。手引きを止めたら行を消す。
- front matter にするのは、窓口と検査スクリプトが本文を読まずに判定でき、会話や担当が変わっても `status.md` から続けられるため（REQ-WF-007）。
- テンプレート（`sdd-change-intake/templates/status.md`）には置かない。伴走は頼まれたときだけ始め、ふだんの案件の項目を増やさないため（NFR-WF-003）。
- 検査スクリプトは、`guide` があれば値が `on` かを確かめ（違えばエラー）、案件の要約に「手引き: あり」の1行を出す（JSON では `summary.guide` を真偽値で出す）。ないときは何も出さない。状況確認と再開は要約を使うため（DES-WF-006）、別の会話でも伴走中であることが分かる。必須の項目（`FRONTMATTER_KEYS`）には含めない。
- 承認の対象のパスに `status.md` は入らないため、`guide` を足し引きしても再承認にはならない。`guide` の変更は、次の作業の区切りのコミットか承認のコミットに `status.md` と一緒に含める。`sdd-guide` はコミットしない。
- 伴走は承認・工程の規則を変えない。練習用の案件やファイルは作らない。

### 窓口の受け持ち

窓口（`sdd-orchestrator.agent.md`）がガイドについて持つのは、次の3点だけとする。手順の本体は `sdd-guide` にあり、窓口は必要なときだけ読む（DES-COM-007）。

1. 依頼表: 「使い方を教えて・次は何をすれば・手引きして・手引きはもういい」は `sdd-guide` を使う。
2. 工程の区切り（進め方）: `status.md` に `guide: on` があれば、区切りの応答に `sdd-guide` の伴走の案内を添える。ないときは添えない。
3. 守ること: 工程の作業（開発・設計・実装など）を頼まれたとき、案件がない、または前の工程の承認がなければ、作業を始めず `sdd-guide` の工程の説明で答え、利用者の依頼を受けてから工程を始める。

伴走の案内は窓口だけが添える。壁打ち・承認・状況確認のスキルは伴走の案内を扱わない。工程の区切りの応答は、どの担当に任せた後でも窓口が返すため（DES-WF-005）、窓口の1か所で足りる。他のエージェントの中でスキルを直接呼んだときは、案内を添えない。

### 受付での伴走の開始

受付（`sdd-change-intake`）は、手引きを頼まれていたら、作る `status.md` の front matter に `guide: on` を入れる。テンプレートには置かない。会話の流れの記憶に頼らず、受付の手順で確実に伴走を始めるため（REQ-WF-016）。

### 工程に沿わない依頼

判定は窓口が行う。窓口は工程を進める依頼で `status.md` の `phase` と承認を確かめる（DES-WF-001）。今のブランチに案件がないときだけ、`sdd-guide` が変更 ID なしの検査で他のブランチの進行中の案件を確かめる。

| 状況 | 例 | 工程に沿わない | 窓口の応答 |
| --- | --- | --- | --- |
| 案件がない（今のブランチに対応する `status.md` がなく、変更 ID も示されていない） | 「ログイン画面を開発して」「この機能を実装して」 | はい（作る対象が書かれていても受付の依頼ではない） | 受付を始めず、標準と軽量の流れ、受付から始めること、受付の依頼の言い方を示す。進行中の案件があれば候補として示し、続きなら「<変更ID> を再開して」、新しいものなら受付の依頼の言い方を案内する。候補は、今のブランチの `docs/spec/changes/` で `state` が `done` でない案件と、変更 ID なしの検査の「他のブランチの進行中の案件」（DES-TOOL-003）から作り、成果物は読まない |
| その規模の工程で前の工程の承認がない | 要件の承認のない標準の案件で「実装して」、要点の承認のない軽量の案件で「実装して」 | はい | 今の工程、残りの承認、今の工程を進める依頼の言い方 |
| 始めたい・作りたい・直したい・考えたい（始める意思や相談） | 「〜を作りたい」「〜を直したい」「新しく始めて」 | いいえ（受付の依頼） | 受付を始める（案内は添えない） |
| 区切りでの次の工程の依頼、後の工程の案の作成やレビュー、壁打ち・質問整理・深掘り・状況確認 | 「続けて」「設計の案だけ作って」 | いいえ（REQ-WF-003・012） | ふだんどおり（案内は添えない） |

- 言い方の一覧で判定しない。例は手がかりで、依頼が「受付・壁打ち」（始める意思や相談）か「成果物を作る工程の作業」（作ること自体の指示）か、その工程の前提の承認があるかで決める。迷うときは受付を始めず、工程の説明で答えてから利用者に選んでもらう。
- 説明の後は止まる。利用者が勧めた工程を頼んだら始める（「はい」「それで」も依頼として扱う）。

### 確かめ方

対話の動作はローカルに登録したプラグインを使った Copilot Local での試行で、形はテスト（`npm test`）で確かめる（DES-DEV-004 の方法に合わせる）。

| 受入条件 | 確認方法・期待する観測 |
| --- | --- |
| AC-WF-013 | 試行: 「承認はどう答えればいい？」で、ユーザーガイドの「判断と承認の答え方」の節へのリンク付きの短い答え。ユーザーガイドにない質問で「見当たらない」と答える。続けて「もっと詳しく調べて」で、導入・管理ガイドなどの根拠のパス付きの答え。前後で `git status --short` が変わらない。レビュー: `sdd-guide` にユーザーガイドの本文（工程の説明・依頼の例）が写されていない |
| AC-WF-014 | 試行: 要件の承認待ちの案件で「次は何をすればいい？」と聞き、工程・次の作業・依頼の言い方・必要な判断が示され、設計が始まらない。検査スクリプトの実行と `status.md` のほかに成果物を開いていない（ツールの実行の記録で確かめる）。案件のないブランチで受付の始め方が示される。前後で `git status --short` が変わらない |
| AC-WF-015 | 試行: 「手引きして」で `status.md` に `guide: on` が入る。次の承認の後の応答に3行以内の案内が付く。新しい会話で同じ変更 ID の再開を頼み、区切りの応答に案内が付く。「手引きはもういい」で行が消え、次の区切りの応答に案内が付かない。`guide` のない案件の区切りの応答に案内が付かない。テスト: 検査スクリプトが `guide: on` を要約に出し、`guide: yes` などをエラーにし、`guide` がなくてもエラーにしない |
| AC-WF-016 | 試行: 案件のない状態で「開発して」と頼み、ファイルとブランチが変わらず、標準・軽量の流れと受付から始めることが示される。要件の承認がない標準の案件で「実装して」と頼み、今の工程と残りの承認（requirements・design）が示され、`tasks.md` もコードも作られない。main など案件のないブランチで、ローカルの `change/<ID>` ブランチに進行中の案件があるとき、その案件が変更 ID・工程・状態・ブランチ名付きで候補として示され、受付もブランチの切り替えも始まらない。テスト: 検査スクリプトが他のブランチの進行中の案件を一覧にし、今のブランチにある案件・`done` の案件・`branch` がそのブランチと違う案件を含めず、実行の前後でファイルと今のブランチが変わらない。要点の承認がない軽量の案件で「実装して」と頼み、同じく実装が始まらない |
| 共通 | テスト: スキルが15になり、`sdd-guide` の名前と手順の形（入力・手順・停止・出力）が合う。窓口の依頼表に `sdd-guide` へのリンクがある。プラグインの中のリンク切れがない。リポジトリ版の書き出しで `sdd-guide` からユーザーガイドへのリンクが `.github/sdd/user_guide.md` を指す |

- リポジトリ版では、導入・管理ガイドへのリンクが URL に書き換わる（DES-TOOL-007）。「詳しく調べて」でその URL を読めない環境では、URL を示して、手元で読める文書だけで答える。
