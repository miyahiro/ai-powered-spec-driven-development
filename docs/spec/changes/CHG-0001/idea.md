# 仕様成果物の機能大分類と番号付けの改善（CHG-0001）

状態: 検討中（案。合意・工程承認済みではない）
入力・出所: 変更受付 CHG-0001（`docs/scratchpad/CHG-0001/state.json`）、壁打ちでの宮下さんの回答（2026-10-19）、現行の [要求定義書の目次](../../current/requirements/README.md) と [common.md](../../current/requirements/common.md)

## 目的と課題

- 目的（人の意向）: 要求・設計などの仕様成果物を大きな機能分類ごとに整理し、番号と分類の関係を人が確認しやすくする。
- 確認された課題（人の回答）:
  - 要件 ID や設計項目がどの機能に属するか分からない。
  - 要求から設計、タスクへの追跡がしづらい。
- 現行の観察（事実。`docs/spec/current/requirements/` の確認結果）:
  - 要求は `REQ-WF-001`、機能は `FUN-WF-001`、大分類は `CAT-FLOW` と表記され、略称が `WF` と `FLOW` で食い違う。
  - 大分類は 6 つ（FLOW / AUTHOR / CANON / DEV / GUARD / SETUP）で、文書は 5 つ。分類と文書が 1 対 1 ではない。例えば `FUN-SPEC-001〜005` は AUTHOR、`006〜009` は CANON に属し、同じ文書内で分類が分かれる。
- 仮説（未確認）: ID の略称が分類と一致すれば、人が ID だけで所属を判断できる。

## 対象者・利用場面

- 対象者（人の回答）: AI が生成した要件・設計の内容を確認する人。
- 場面（人の回答）: 承認、レビュー、プロジェクトの引継ぎ。
- 適用先（人の回答）: このエージェントを既存プロジェクトへ適用する場合は、そのプロジェクトの既存設定・既存の番号体系に従う。

## 期待する価値

- 所属する分類と、要求から設計・タスクへの対応を、人が短時間で確かめられる。
- 確かめ方（案）: 既存の要求から数件を選び、新しい ID と一覧表だけで所属と追跡先を答えられるかを、確認者が試す。

## 採用案と理由

- 推奨案・理由（AI）: 候補 1 + 3 + 4（候補 1・3 は人が採用と回答済み。候補 4 は質問 4 の回答待ち）。人が ID だけで分類を判断でき、欠番の意図と俯瞰的な追跡も確認できるため。候補 2 は影響が大きいため見送り。
- 人の判断・出所（宮下さんの 2026-10-19 の回答）:
  - 分類コード付きの番号を希望する。人にも理解しやすく追いやすくする他の方法の提案を求めている。
  - 機能大分類は「このままでよい」。現行の 6 分類（FLOW / AUTHOR / CANON / DEV / GUARD / SETUP）を維持する（質問 1。宮下さんの回答、2026-10-19）。
  - 番号は欠番にする（再利用・詰め直しをしない）。
  - `docs/spec/current/` は新ルールへ移行する。ただし、適用先プロジェクトでは既存設定に従う。
  - 略称を分類コードへ統一する（候補 1）。ID・参照の置換が広範囲になることも許容する（質問 2。2026-10-19）。
  - 欠番台帳（候補 3）を設ける（質問 3。2026-10-19）。
  - 複数分類に跨ぐ項目（共通要件）は主分類に置き、他分類から参照する（質問 7。2026-10-19）。
- 保留: 候補 4（分類別一覧表）の更新方法は未回答（質問 4）。
- 注記: 上記の回答は壁打ち・要求定義の工程承認ではない。

## 対象範囲

- 今回の対象: 要求・設計などの仕様成果物の機能大分類と番号付けの改善。仕様成果物を生成する SDD 用 Agent・スキルの記述規則の改善。直接関連するテンプレート・ガイドの整合。`docs/spec/current/` の新規則への移行。
- 対象外: CHG・TASK などの管理 ID の番号体系の変更。番号・分類に関係しない機能変更。適用先プロジェクトの既存文書の書き換え（既存設定に従う）。
- 将来の候補: 分類と文書のファイル構成の 1:1 化（候補 2）。

## 前提・制約

- 確認済み（人の回答）: 欠番にする。適用先は既存設定に従う。
- 確認済み（事実）: 現行文書は分類コード付き ID を既に使っている。
- 未確認の仮説: 規則の正を `common.md` に置き、Agent・スキル・テンプレートは要約と参照にする構成が適する（利点・欠点は下記の質問 6）。
