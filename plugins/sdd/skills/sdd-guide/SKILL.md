# ガイド

入力: 利用者の言葉、任意の変更 ID。前の工程の承認は不要。

答えの中身は [ユーザーガイド](../../user_guide.md) などの文書から引き、このスキルには持たない。ファイルを変えるのは `status.md` の `guide` の行だけ。工程も受付も始めない。ブランチを切り替えない。承認しない。コミットしない。

今のブランチは `git status`（読み取り）で確かめてよい。それ以外の Git のコマンド（`branch`・`show`・`for-each-ref`・`ls-tree` など）は実行せず、案件とブランチの一覧は [sdd-spec-check](../sdd-spec-check/SKILL.md) の出力（要約と「他のブランチの進行中の案件」）と今のブランチの `docs/spec/changes/` から作る。

1. 入力の言葉から、下の5つの場面のどれかを選ぶ。選べなければ、どれを求めているかを1問で聞く。
2. 場面ごとに、表の「読むもの」だけを読み、「出力」の形で答える。読むのは必要な節だけとし、案件の成果物（要件・設計・タスク・コード）は読まない。

   | 場面 | 読むもの | 手順 | 出力 |
   | --- | --- | --- | --- |
   | 使い方の回答 | ユーザーガイドの [目次](../../user_guide.md#目次) と、該当する節だけ | 目次から節を選んで読み、その記述だけで答える。根拠になる記述がなければ推測で答えず、「ユーザーガイドには見当たらない」と伝え、「詳しく調べて」と頼めば関係する文書まで見ることを1行添える | 数行の答えと、根拠の節へのリンク |
   | 詳しく調べて | [導入・管理ガイド](../../README.md)、[共通ルール](../../common-rules.md)、エージェント・スキルの定義のうち関係する節だけ | 頼まれたときだけ読む。答えは読んだ文書に書かれていることだけにし、書かれていない手順・設定例・コマンドを作らない。それでも答えがなければ、分からないと伝える。導入・管理ガイドが URL で読めなければ、URL を示して手元で読める文書だけで答える | 答えと、根拠の文書のパス |
   | 次の作業の案内 | [sdd-spec-check](../sdd-spec-check/SKILL.md) の要約（変更 ID 付き）、必要なら `status.md`、ユーザーガイドの [区切りごとの依頼の例](../../user_guide.md#区切りごとの依頼の例)。案件が決まらないときは、変更 ID なしの検査の「他のブランチの進行中の案件」 | 変更 ID は今のブランチ（`change/<ID>`）から推す。決まらなければ、今のブランチの `docs/spec/changes/` で `state` が `done` でない案件と、他のブランチの進行中の案件を候補として示し、選んでもらう。他のブランチの案件が選ばれたら、一覧の工程・状態とブランチ名を示し、「<変更ID> を再開して」と頼めば窓口が確認してから切り替えることを案内する（自分では切り替えない）。候補がなければ、ユーザーガイドの [案件を始める](../../user_guide.md#2-案件を始める) から受付の始め方を示す | 今の工程と状態、次の作業、それを始める依頼の言い方、必要な判断（承認・期限の来た質問・再承認・ブランチの不一致） |
   | 伴走の開始・停止 | `status.md` の front matter | 開始: 案件があれば front matter の最後に `guide: on` の行を差分で加え、下の伴走の案内を返す。案件がなければ受付の始め方を示し、続けて受付をするなら、受付（[sdd-change-intake](../sdd-change-intake/SKILL.md)）に手引きを頼まれていることを伝える。停止: `guide` の行を消し、以後は案内を添えないことを伝える。`off` は書かない | 開始・停止の結果と、今の位置・次の依頼の言い方 |
   | 工程の説明 | sdd-spec-check の要約（案件があれば）。案件がなければ変更 ID なしの検査の「他のブランチの進行中の案件」。ユーザーガイドの [規模（標準と軽量）](../../user_guide.md#規模標準と軽量) と [全体の流れ（標準）](../../user_guide.md#全体の流れ標準) | 窓口が工程に沿わない依頼と判定したとき、または利用者が直接呼んだときに使う。案件がなければ、今のブランチの `docs/spec/changes/` で `state` が `done` でない案件と、他のブランチの進行中の案件を候補として変更 ID・工程・状態・ブランチ名付きで示し、続きなら「<変更ID> を再開して」、新しいものなら受付の依頼の言い方を案内する。受付も工程の作業もブランチの切り替えも始めず、説明の後は止まる | 規模ごとの工程の流れ（節へのリンクと数行）、今どの工程から始めるべきか、残りの承認、その工程を始める依頼の言い方 |

3. 依頼の言い方は、ユーザーガイドの区切りごとの依頼の例から引く。自分で作った言い方を固定のコマンドのように示さない。
4. 伴走の案内（伴走中に工程の区切りの応答へ添えるもの）は、次の3行以内の形にする。区切りの直後は、更新したばかりの `status.md` の `phase`・`state`・承認・次の作業から作り、検査をもう一度実行しない。

   ```text
   手引き: 今は <工程>（<状態>）です。
   次は「<依頼の言い方>」と頼んでください。
   あなたの判断: <承認・質問への回答など。なければ「なし」>
   ```

5. 伴走は承認・工程の規則を変えない。練習用の案件やファイルを作らない。`guide` の変更は、窓口が次の区切りのコミットか承認のコミットに `status.md` と一緒に含める。

停止: 案件を選べない。使い方の回答で、ユーザーガイドを読めない。

出力: 場面ごとの「出力」の形の答え。伴走の開始・停止のときだけ、`status.md` の `guide` の行を変えたこと。
